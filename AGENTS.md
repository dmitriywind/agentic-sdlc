# agentic-sdlc

A portable software factory: a Claude Code plugin and a CLI, shipped from Git (not npm).
`references/architecture.md` is the contract; read it before you change any part.

## Layout

- `skills/` the skill pack (plugin layout: `skills/<name>/SKILL.md`); `init` copies it to a project's `.agents/skills/`.
- `scorers/` judge scorer definitions; `init` copies them to `.agents/scorers/`.
- `src/` the CLI (`agentic-sdlc`): board, forge and VCS ports, gates, dispatch, ledger, bench, MCP server, init/validate/doctor.
- `templates/` what `init` installs: `binding.yml`, `gates/github/` (the workflows, the issue form, the rulesets), `gates/hooks/pre-push`, `runner/` (the cloud routine and other schedulers, prompts, setup), `bin/` (the launcher), `mcp/`. `templates/known-hashes.json` is written by the build.
- `.claude-plugin/` the plugin and marketplace manifests; `agents/` the plugin's subagents; `hooks/` the guard and session-start hooks and the MCP launcher.
- `references/architecture.md` the contract; `docs/` the guide, `docs/platform.md` and the roadmap. `docs/guide.html` is generated by `scripts/guide.mjs` from `docs/guide/*.md` (the text), `scripts/guide/shell.html` (the page) and `scripts/guide/components/*.js` (the interactive parts) (`npm run build`): edit the Markdown, never the page. `features/` the behaviour: executable Gherkin features (`features/<area>/*.feature`), their steps (`features/steps/`) and the runner (`features/support/`), run on node:test.

## Commands

- Build: `npm run build` (dist/, docs/guide.html and templates/known-hashes.json; commit all three)
- Typecheck: `npm run typecheck`
- Test: `npm test` (builds first; runs every feature). Features only: `npm run test:features`; one feature or scenario: `FEATURE=gates/approval` or `SCENARIO='Fast-lane'` before it
- Plugin manifests: `claude plugin validate .` and `claude plugin validate .claude-plugin/plugin.json`
- `agentic-sdlc gate skill-regression`, `validate` and `doctor` need an installed project (`.agents/binding.yml`); this repo does not run its own factory.

## Rules

- A process rule lives only in `skills/`. A project value lives only in the binding. `src/` holds mechanism only.
- A skill calls `agentic-sdlc board|forge|vcs <verb>`, never a vendor CLI.
- A change to a port, a binding key or a skill's interface changes `references/architecture.md` in the same change.
- A change to what a skill, gate, hook or `init` does changes its feature in `features/` in the same change, and the guide chapter in `docs/guide/` that tells that part of the story. The source holds the rule; the feature states the behaviour, runs, and points to the source; the guide points to the feature.
- `docs/roadmap.md` is this repo's backlog. A finished item leaves it; the git log and the release tags are the history. Keep no audit, changelog or history file: a rule lives in the source, a plan in the roadmap.
- Keep `.claude-plugin/plugin.json` `version` equal to `package.json` `version`.
- Git only, no npm: the npm name `agentic-sdlc` is another project. `dist/` is committed (the plugin and `github:` installs run it), so run `npm run build` and commit `dist/` with every `src/` change. A release is a `v<version>` tag.
- Git only, trunk-based. The trunk is `master`. No long-lived branch. A change branch is `feature/<name>` and a release branch is `release/<version>`; no branch sits outside these two folders. Every change reaches `master` through such a short-lived branch and a pull request that is squash-merged once the CI check `test` passes on an up-to-date branch (`gh pr create`, then `gh pr merge --auto --squash`). The `master` ruleset has no bypass, so a direct push is refused. Tag a release only after its pull request merges and CI on `master` is green; the `release tags` ruleset refuses to move or delete a `v*` tag, so a bad release is followed by a new version.
